Rekindled · Optimization

Performance

Cut allocation hotspots throughout the spell and physics systems: preallocated buffers, object pools, frame throttled queries, and a VFX GPU readback workaround that prevents effects from being recycled before they finish.

Zero Allocation Spell Raycasts

The spell indicator (the decal showing where a zone spell will land) updates every frame while the player aims. Without care that is a physics query allocating a new array each tick, multiplied by every active spell behavior.

  • A RaycastHit[5] field on SpellBehavior (the base class all spells inherit from) is allocated once at construction. Physics.RaycastNonAlloc fills it in place with no heap traffic per frame.
  • A Collider[8] field on AimPivotController (the component that owns camera aim and target lock) serves the lock on overlap sphere. Same pattern: allocated once, reused every search.
  • A Collider[10] field on Torch serves the Scorched Earth proximity check. Shared across all three lighting modes so there is a single buffer per torch regardless of which mode fires.
Before
RaycastHit[] allocated every frame inside the aim point loop. 60fps = 60 arrays per second per active spell behavior.
After
RaycastNonAlloc with a preallocated RaycastHit[5] field. Zero heap allocation in steady state. GC pressure from spell raycasts: eliminated.
Lock On Query Throttle

The lock on system runs an OverlapSphere every frame to find valid targets in range. In enemy dense areas that is expensive, and the lock target changes slowly enough that it does not need to run every frame.

  • LockSearchInterval = 3: the search only runs every third frame. The locked target is held between searches. There is no perceptible lag at 60fps, and the physics query cost drops by two thirds in dense areas.
  • The throttle counter increments in LateUpdate. A spell switch resets it immediately so the first search after switching always runs on the next frame.
Projectile Pooling

Homing Feather fires up to 8 projectiles per cast. Without pooling each cast Instantiates 8 objects and destroys them on impact, causing GC spikes on every attack.

  • ObjectPool<HomingProjectile> in HomingSpellBehavior. Default capacity 4, max size 8. Get from pool sets the projectile active and positions it; return to pool deactivates and zeroes velocity.
  • Pool warmup happens at spell Initialize, not at first cast, so the first feather volley never triggers an allocation spike mid combat.
  • FireSpitter traps use the same ObjectPool<DamageOnTrigger> pattern. A closure captures the return to pool callback and cancels the lifetime coroutine if the projectile hits early, so the pool is always returned exactly once per projectile.
VFX Graph GPU Readback Bug

Unity's VFX Graph (the node based particle system used in Rekindled) reports particle counts via async GPU readback, which takes a few frames to settle. Before it settles, aliveParticleCount returns a large negative integer, not zero.

  • The bug: VFX completion checks used aliveParticleCount == 0. Before readback settled the count was negative and never equalled zero, so effects ran indefinitely or never autocompleted.
  • The fix: changed all completion guards from == 0 to <= 0. Negative garbage values before readback settles are treated as done. Once the GPU readback stabilizes, the real count of 0 also satisfies the guard.
  • Pooled VFX init sequence: on retrieval from pool, both Reinit() and Play() must be called. Reinit() alone is silent if the VFX asset's initial event is not set to "OnPlay", causing the effect to visually reset but never start emitting.

Why does aliveParticleCount go negative? The VFX Graph reads particle counts from the GPU via async readback. The CPU sees a stale value from the previous readback until the GPU finishes. Unity's internal representation of "no data yet" produces large negative integers in some driver configurations.

FireSpitterGroup: Offscreen Culling

Fire spitter traps should only run their spawn loops when the player is nearby. Running them offscreen wastes CPU and pool budget on projectiles the player will never see.

  • FireSpitterGroup does an OverlapSphere check each frame against the player's position. If the player is beyond activationRadius, all child spitters stop their InvokeRepeating shoot loops and return inflight projectiles to the pool.
  • A state change guard ensures StartShooting and StopShooting only fire once on transition. Without it the guard condition triggers continuous calls every frame the player is out of range.
