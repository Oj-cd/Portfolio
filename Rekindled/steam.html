Rekindled · Platform Integration

Steam Integration

Shipped Rekindled on Steam. Integrated Steamworks.NET (a C# wrapper around Valve's Steamworks SDK), fixed three bugs in the boilerplate SteamManager, wired achievement unlocks as a data driven listener, and extended the achievement data structure to bridge the game's internal events to Steam's API.

Integration Setup

Steamworks.NET is a thin C# wrapper around Valve's Steamworks SDK. Getting it running correctly in Unity without going through the Steam client requires a few non-obvious steps.

  • steam_appid.txt placed at the project root with the game's App ID (4926530). This lets SteamAPI.Init() succeed inside the Unity editor without launching through Steam.
  • RestartAppIfNecessary configured with new AppId_t(4926530) instead of AppId_t.Invalid so the running build correctly identifies itself to Steam. Without this, Steam does not recognize the process as the correct app and features like overlay and achievements are silently unavailable.
  • SteamAPI.RunCallbacks() called every Update frame. Steamworks is callback based; skipping this means no Steam events are ever dispatched.
SteamManager Bug Fixes

The Steamworks.NET package ships a boilerplate SteamManager.cs. It had three bugs that cause silent failures or exceptions in production.

Bug 1: Static state corruption on duplicate Awake

Original code assigned s_instance = this before the s_EverInitialized check. If a second SteamManager was instantiated (for example a scene reload with DontDestroyOnLoad), the static instance was overwritten before the duplicate was destroyed, corrupting state.

Fix: moved the assignment to after the duplicate check so s_instance is only set when the object is confirmed to be the first and only instance.

Bug 2: Exception on duplicate init instead of graceful destroy

The duplicate detection path threw an exception, crashing the game with a visible error rather than silently destroying the extra instance.

Fix: replaced throw with Destroy(gameObject); return;. The duplicate is cleaned up quietly and the first instance continues unaffected.

Bug 3: Initialized property auto-spawning a new manager

The Initialized getter read through the Instance property, which had a lazy spawn side effect. Reading Initialized on a frame before SteamManager existed in the scene would instantiate a new one mid frame.

Fix: rewrote the getter to read s_instance directly: return s_instance != null && s_instance.m_bInitialized;. No side effects.
Achievements

Achievement unlocks are data driven. Adding a new achievement that maps to a Steam API name requires only a data asset change, no code.

  • A steamApiKey field was added to the Achievement struct in GlobalDefinitions.cs. The field stores the Steam API name exactly as defined on the Steamworks dashboard (e.g., "ACH_FIRST_BOSS"), bridging the internal achievement object to the Steam API.
  • SteamAchievements.cs subscribes to OnAchievementUnlocked via MessagingService. On receive: checks SteamManager.Initialized and that achievement.steamApiKey is non-empty before calling SteamUserStats.SetAchievement().
  • StoreStats() is called immediately after SetAchievement. Without StoreStats the unlock is queued locally but never written to Steam's servers. On a crash, the achievement would be lost.
private void HandleAchievementUnlocked(Achievement achievement)
{
    if (!SteamManager.Initialized) return;
    if (string.IsNullOrEmpty(achievement.steamApiKey)) return;
    SteamUserStats.SetAchievement(achievement.steamApiKey);
    SteamUserStats.StoreStats();
}

Why check Initialized rather than catching exceptions? SteamUserStats calls silently fail and return false when Steam is not initialized, but an unchecked call during editor testing (where Steam may not be running) can leave the Steam overlay in a bad state. An explicit guard makes the behavior predictable in both editor and build.
